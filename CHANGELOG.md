# Changelog

## v0.18: the reviewer, and the bound that is no longer there

2026-09-20

v0.17 made what a run has spent the thing that bounds it, and left the walk that used to do the job still running beside it, deriving a number nothing reads. That goes first, because a program with two bounds where one is dead is a program that lies to whoever reads it next, and because it is the one goal of that version that did not land.

- `reviewer.py`, the factory's second program and the first it wrote from nothing: a cold session over a delivered tree that reads and cannot write. The model is offered `list`, `read` and `search` and the tool its report returns through, and never `write`, `edit` or `check` -- not refused at a wall, never offered, because a model told it has a hand it does not have spends calls discovering otherwise. It builds no container and runs nothing of the project's. The confinement, the wire, the record, the key scan the store insists on and the caps are the builder's, reused rather than rewritten.
- A review is five independent passes per dimension and four dimensions, each dimension a goal a pass pursues rather than a question it may answer briefly, and each one there because something got past a green check: a change that satisfies its tests without meeting the goal; a claim the goal makes that no test would catch being broken; work the program already does; what now describes something that is gone. No pass is told what another found. What two or more passes of one dimension reached is reported, what one reached alone stays in the record, and two passes found the same thing when they name the same path and line -- never by their prose, which would need a second model's judgement. The answer says how far the passes agreed and never that a contract is met, because no number of passes can warrant that.
- The dimension is the last thing in the prompt, so all twenty sessions share one cached prefix. Not a matter of taste: measured on the first real review, 95% of its input was served from cache, which turned $1.18 of input into $0.25. It costs nothing to get right and nothing catches it when it is wrong.
- A role says where its model is served. `base_url` had been read from the configuration since v0.15 and used by nothing, so the reviewer role this host configures would have sent **another vendor's key to DeepSeek** in an `Authorization` header, for a model DeepSeek does not serve, with the wire redacting the header so the record would not have shown it. Found before the first real run.
- The walk is gone, which is what v0.17 owed. `call_budget` and everything only it used -- `CALLS_FLOOR`, `CALLS_CEILING`, `SHARE`, `RESERVE`, `REPORT_REQUESTS` -- are removed, `limits` takes no argument, `run` lost its budget and `Tools` carries none. What bounds a run is what it has spent; `CALLS_LIMIT` and `REQUEST_LIMIT` are fixed constants above it, a cheap counter for a runaway that spends nothing.
- Two defects the first real review of the reviewer found, in twelve minutes against a live model, after a written Goal, red tests, a green suite and an independent review had all passed it. The spend ceilings were measured on builds and a build is one session, so five sessions sharing one budget died against them: a pass is now bounded by its own spend and the review stops starting passes once it has spent what its passes were worth. And `review.json` was written only when a run ended in an answer, so that review produced no readable report at all while its own numbers carried three findings and an agreement of 0.6 -- [[the-work-a-capped-run-leaves]] one layer up.
- Two review notes in `docs/reviews/`, fifteen findings between them, every one verified before it was written down. Ten single-line mutants that passed the whole suite are now killed, among them deleting the key scan, narrowing it to this run's own key, telling the reviewer it could write, and rooting its tools at `/etc`.

## v0.17: what a run costs, and what its work is worth

2026-09-20

v0.16 gave a run a bigger budget and a way to land inside it; reading the records afterwards said the budget was derived from a fiction and that the money was somewhere else entirely. Seven of thirteen capped builds left a tree the builder's own check had passed, and every one was thrown away for want of a report -- ninety cents, seventeen per cent of everything this factory has ever spent on builds, finished work binned because nobody wrote five bullet points about it. This version takes that work. It also stops pretending the budget measures reading: decomposed, the walk counts files, and more than half of what it counts is the vault and the evaluation set the builder never opens. What replaces it is the quantity the budget was always a proxy for -- what a run has spent, which the records separate cleanly: a ceiling at $0.125 sits above every one of the 85 builds that answered and below six of the thirteen that were capped. The factory prices that itself, and the version's second finding is why it must: the library's table has no row for the model we run, and the row for the name next to it belongs to a different model. Our own constant was right all along, and it was labelled a fallback.

- A build is taken when the tree it left passes the check, whatever ended the run. `build.py` stops treating a cap as a reason to refuse: a capped run that left a green tree with a diff is pushed like any other build, one commit, never forced. What still refuses is what must -- a red check, a check that never ran, a green check that changed nothing, a branch that moved, and a record the store would not take. That last one no longer rides on the exit code, which a capped run and a refused record now share: the store's own git is asked whether it holds the record, and a store that cannot answer answers no, because a record the store would not take may hold a key.
- The commit says where it came from. A build taken from a run that never reported carries `Stopped-By` beside `Built-By`, so a reader of the branch knows whether the work arrived with a report without holding the store. `Built-By` reads exactly as it did, which the gate's own checker was run against a two-trailer commit to prove.
- A run is bounded by what it has spent. `price(usage)` is the one place tokens are priced, so the number the tools land on and the number the record carries cannot drift. `Tools` is given something to ask, and asks it at every call rather than once, because a run crosses the line in the middle: at `SOFT_SPEND` of $0.125 all six tools refuse and say report now, and at `HARD_SPEND` of $0.25 the run itself ends and the record names `spend` as the cap that did it. The ceiling is measured rather than chosen -- it is above every one of the 85 builds in the store that answered and below six of the thirteen that were capped, and no threshold in tool calls, requests or wall-clock separates those two populations at zero cost to the answered runs.
- The price table is this model's source and not a fallback. `genai_prices` has no row for `deepseek-flash`, and the row for the adjacent name is a different model's numbers -- 0.43x our cache-hit rate, 0.68x our input and 0.91x our output, which is no discount of anything. Ours are DeepSeek's published peak rate for the model we run, checked against their page on 2026-09-20. The seed that proposed renaming the model so the library could price it is rejected: it would have replaced a correct number with a wrong one. The rate stays flat where DeepSeek's halves outside 01:00-04:00 and 06:00-10:00 UTC on weekdays -- 85% of the store's runs started outside those windows, so the records overstate the money by 1.61x, $6.53 against $4.07, and that is the right trade: a bound must measure the work, not the hour, or the same tokens would buy twice the work at midnight.
- A green the final check could not confirm is not a green. `check_final` still swallows a sandbox that cannot run, because a record must survive one, but the record no longer keeps a verdict that stands for a tree that check did not see: `check` says nothing instead. Found by review, and it mattered only because of the first bullet -- until a capped run's work could be taken, a stale green decided nothing.
- The check's container holds 1024 tasks rather than 256. **The one change of this version the factory did not write.** The suite crossed the old limit mid-version and every build afterwards was refused for a reason that had nothing to do with what the builder wrote; two builds diagnosed it correctly and were thrown away anyway. It is accumulation, not a peak -- every module passes alone at 256 and the suite together does not -- and the factory could not fix it, because a candidate build is judged by the check that is failing and that check is run by the instance at its pinned tag. What was raised is a fork-bomb guard, not a wall; the mount, the network, the memory and the CPUs do not move. Why the suite holds so many at once is `the-tasks-the-suite-never-gives-back`, which says to measure the curve and not to raise the number again.
- The review of the version's first build is in `docs/reviews/`, with seven findings, every one verified before it was written down. Two were demonstrated with mutants that pass the whole suite: one that asks whether the store holds any commit rather than this record, which pushes a leaked key onto the branch, and one that refuses only a red check, which pushes a tree no check has seen. Both clauses are now pinned, and both guards were confirmed to kill their mutant.

## v0.16: a budget the checkout earns, and a landing at the end of it

2026-09-20

The caps were set at v0.3, when `builder.py` was three hundred lines and the suite thirty tests; the checkout the builder now works on is 13,044 lines the tools can reach across 142 files, and the caps have not moved. v0.15 spent seventy-eight per cent of its money on runs that were cut off, four of them with the check green and the whole change made, and nothing the spec could do reached them. This version makes the budget a function of what the run must read and gives the run a landing: the tools stop and say report now when the budget is spent, and the requests are derived from the calls so that a run always has the requests left to say what it did. The two caps have bound the same run at nearly the same place since v0.3: at the median 1.22 tool calls a response, eighty calls is about sixty-six requests against a cap of sixty, so whichever the run's own ratio favours runs out first -- eight of the thirteen capped builds in the store ended on the requests and five on the calls. Neither can land a run, because both are the library's hard limits with nothing underneath them, which is why the soft landing the tools already use for writes and checks has never fired for a run as a whole.

- A run's budget is the checkout's rather than the program's: `call_budget` walks every file the tools can reach, sums the reads each one costs at `READ_LINES_CAP` lines a read, takes a share of that pass and adds the writes and checks a run is already allowed, floored at the 80 the tool-call cap held since v0.3 and bounded by a ceiling so the worst a run can cost stays a number. On this checkout it is 137 tool calls where the constant was 80, and 175 requests where it was 60. **Read the derivation with care**: decomposed after the fact, 156 of its 182 reads are the one-per-file floor and only 26 come from the division, so it counts files rather than lines, and more than half of what it counts is the vault and the evaluation set, which the builder does not read. The number is defensible and the route to it is not; [[the-budget-that-counts-files]] carries the measurement and replaces it.
- A run that spends its budget lands instead of being cut off: the tools count every call made through them, refused or not, and all six then answer `cap reached; report now` in the words the write cap and the check cap already use. `TOOL_CALLS_CAP` and `REQUEST_CAP` are gone, and the library's two limits are derived from the one budget -- the calls it allows are the budget and a reserve, the requests are those and a few more -- so a run that has spent every call it was given still has the requests to say what it did.
- A run is given one budget by one route: `run` takes it as an argument with no default, so the number the tools refuse at and the number the library enforces cannot differ, and nothing is carried on the library's own agent to make that so. The reserve above the budget is wide enough to absorb a whole response, because the library admits or refuses a response's tool calls together and a response wider than the reserve would cross the limit before any of it ran -- the landing not firing, which is the fault this version exists to remove.
- The record carries the caps beside the counts they bound, `calls_cap` beside `tool_calls` and `requests_cap` beside `requests`, and `cap` says which one ended the run, `calls` or `requests`, or nothing when none did. `runs.py` shows all three, so a version can read off its own table whether a run was cut off or went wrong instead of reading `detail` by hand.
- The search that keeps a key out of a record no longer fails open on a configuration that names no key. `configured_keys` swallowed the error a missing or malformed `roles` raises and answered with an empty list, so the record was committed having been searched for nothing; it now refuses the commit naming the configuration's file and which fault, as an unreadable key file already did, and an empty list of keys is refused whatever produced it.

## v0.15: the roles an instance runs

2026-09-19

The instance's configuration stops being two paths and becomes a description of the roles the instance runs: each names the model that role runs on and the file its key is read from, so a second model is expressible without editing the program — which is what a reviewer stronger than the builder needs, and the reason this version exists. The wall that keeps a key out of a record searches every record for every key the configuration names, not the one key the run was given, so a run made on one provider cannot commit a record carrying another's; and a configuration that cannot say which key a run uses is refused rather than quietly answering with the program's own. It is the first version built by the one before it: an instance pinned at the v0.14 tag, answering a pushed branch through `build.py`, and every commit here carries the tag it was built at.

- The instance's configuration describes the roles it runs: a `roles` table, one entry per role, each naming the `model` that role runs on, the `key` file it reads and optionally a `base_url` for a model served elsewhere. `instance.py` reads them as it reads `records` and `work`, answering with a key's place and never its value, and refusing a `roles` that is missing or malformed in the shape the rest of the configuration is already refused. The builder runs as the role `builder`, so its model is no longer a constant of the program, and a configuration that cannot say which key a run uses is a usage error before the model is called.
- The search that keeps a key out of a record searches every record for every key the configuration names, not the key the run was given, so a run made on one provider cannot commit a record carrying another's; a key file the configuration names that cannot be read refuses the commit too, because a key that cannot be searched for cannot be shown to be absent.
- A version is built by the version before it: an instance is a checkout of the factory's code pinned at a released tag with a configuration of its own, installed by a clone and `uv sync`, and README says how one is installed and moved to a tag.

## v0.14: a build asked through git

2026-09-18

The factory works as a deployment that is sent a seed of a project: `build.py` takes a repository, a branch and a seed's path, and answers with one commit pushed to that branch, or leaves the branch alone and a note on the head it was asked of. A build's record no longer lives in the project it built: it is the factory's log of its own work, kept in a store outside every checkout that the instance's configuration names, which the builder writes, searches for the key's value and commits itself. This repository is the first such project and no exception: seven of the version's seventeen builds were asked for through the command itself, the first the factory was ever sent through git.

- A build's record is the factory's and lives in its store, a git repository outside every project that the instance's configuration names: the builder compresses the wire, searches every file of the record for the key's value, refusing to commit one it cannot read through, and commits the record itself, one commit each; the 146 records this repository tracked were carried into the store and left its tree, and the gate asks nothing of a record, checking only that a build's trailer names a run in the builder's shape.

The instance is a checkout of the factory's code with a configuration of its own, `records` and `work`, and a configuration a run cannot use is refused before the key is read.
- A record's check is the tree the model left: when the model wrote after its last check, the builder checks once more, outside the model's cap, so what a record says was tested is what was left. The gate reads the vault as git tracks it, so the owner's scratchpad inside `docs/` bothers nothing, and the table of records reads the store without importing the model stack.
