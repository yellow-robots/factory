# factory

The factory is `builder.py`: a program that runs a cold model session over a directory, the checkout, until the checkout's tests pass, under walls the model cannot cross. It is built one version at a time and its own repository is its first checkout: since v0.3 its code is written by `builder.py` itself, from tests written before each build, and v0.4 is the first version made that way. What it can do is read off the records of its runs. Nothing in this repository is written for a model to obey; what holds is held by tests, by the tools, by the gate and by git.

You are the attended agent: a model in some harness, resuming this work cold, working with the owner. This file is for any such model. The state of the work is never narrated here; it is derived from git and the files, as below.

## Orient yourself

Run these before reading anything else, from the root of the checkout or worktree you are in:

```sh
uv run gate.py check                                               # the vault against its templates and the repository; silent when they agree
uv run python -m unittest -q                                       # the factory's tests; no provider, no network, no docker
git tag -l --format='%(refname:strip=2) %(objectname:short)'       # the released versions
git log --oneline "tags/$(git describe --tags --abbrev=0)..HEAD"   # what happened since the last one
git status --short                                                 # what is not committed; see the last section
ls docs/versions docs/seeds                                        # the versions and the backlog
uv run runs.py | tail -3                                           # the last run records, as rows of the table
```

Then derive:

- The version in flight is the note in `docs/versions/` whose name is not a tag; there is at most one. Its seeds are the notes in `docs/seeds/` whose `version` names it.
- A seed's stage is its `status`. `open`: evidence and an idea. `spec`: a `## Goal` the builder can be given, read by the gate with the builder's own reader, assigned to a version. `building`: at least one test names it, `seed: <name>` in the test's docstring, committed red. `done`: merged and green. `rejected`: a way out at any stage. `docs/templates/seed.md` states what each status requires and the gate checks it; `docs/backlog.base` ranks the seeds.
- What the builder does and refuses is `README.md`; the walls are the constants at the top of `builder.py`; the exact behaviour is `test_builder.py`. The gate's is `test_gate.py`, the table's `test_runs.py`, the evaluation harness's `test_evals.py`. The model has six tools: list, read, search, write, edit, check.
- A run is a directory in the factory's store, one commit of the store's own git per record, named by its stamp: read `numbers.json` first (`stopped`, `check`, `head`, cost, counts), then `response.md`, `diff.patch` and `wire.jsonl.gz`. The store is not in any project: `records` in the instance's configuration names it, the builder commits each record there when the run ends, and `uv run runs.py` is every record's numbers as one table. The project keeps the build's commit and its `Built-By` trailer, whose stamp points into the store as a commit points at a run, so the builds of a version are `git log --format='%h %(trailers:key=Built-By,valueonly)' tags/<previous>..tags/<version>`, and the run's `head` is the red commit it started from. The gate checks that listing: `check` and `release` read the builds since the highest tag and refuse one whose `Built-By` git does not read as a trailer, or whose value does not end `run <stamp>` in the builder's shape. It asks nothing of the store: a build's record is the factory's and the store's git holds it.
- A review is a note in `docs/reviews/`, named after the record it reviewed, one per independent review: each finding with its severity, whether the attended agent reproduced it, and what it became, `test <name>`, `case <name>`, `seed <name>` or `none:` with the reason. The gate checks the note as it checks a seed, so a release cannot carry a verified finding nobody judged. Every verified defect is judged twice: a test when the factory's code was wrong, a case when the model's behaviour was.
- `cases/` is the evaluation set: one directory per case, a goal, a red test against this repository's own code and the word that says what a pass is, `pass.txt`, each probing a known way for the builder to fail; the harness hides `cases` from the builder's tools for the runs it starts, so the model never reads the word. `uv run evals.py` runs every case three times in throwaway worktrees and prints one table per case; its records are ordinary records whose goal begins `case: <name>`, so `runs.py` shows them beside the builds, and a case with `held_out/` adds `held_out.log` and `held_out.json` of the second check to its records.
- The instance is a checkout of the factory's code with a configuration of its own, `~/.config/factory/instance.toml` or the file `FACTORY_INSTANCE` names, which says three things: `records`, the store; `work`, where a build clones the branch it is building; and `roles`, a table of the roles the instance runs, one entry each naming the `model` that role runs on, the `key` file it reads and optionally a `base_url` for a model served elsewhere. The two paths are absolute and outside every project, a key's place is the configuration's and its value is read only where it is used, and `instance.py` refuses a configuration a run cannot use before any key is read. The builder runs as the role `builder`, so the model is the configuration's and not the program's. A deployed instance is a clone of this repository at a released tag with its environment made from that tag's lock, which is how a version is built by the version before it. On this host the store is `/opt/yellow-robots/factory-records`, local and with no remote, the work is `/opt/yellow-robots/factory-work`, empty between builds, and the instance is `/opt/yellow-robots/factory-instance`; README says how one is installed and moved to a tag.
- The vault is `docs/` as git tracks it: a path git ignores is no note, so the owner's `docs/scratchpad/` bothers nothing, and a wikilink naming an ignored path resolves to nothing.

## How a version is made

The owner and the attended agent choose seeds from the backlog and promote them to specs: a version is assigned, the idea becomes a goal. For each spec the attended agent writes the tests that name the seed and commits them red on a branch. Then either the build command or the builder: `uv run build.py <repository> <branch> docs/seeds/<name>.md` pushes the branch's build back to it as one commit of the factory's, the record already in the store, which is how a deployment of the factory is asked to build a project and how this repository is asked too; or `uv run builder.py <worktree> docs/seeds/<name>.md` builds a worktree in place, and then the attended agent reads the diff and commits it as the factory's work with the `Built-By` trailer. Either way the builder reads the seed's `## Goal` from the checkout's commit, records the seed's name, and the factory writes the code. The attended agent reads the record and the diff and hands the diff to an independent reviewer, a fresh session in this harness that reads the Goal, the diff and the tests and probes the change in throwaway directories; the review's findings go into a note in `docs/reviews/` from its template, each verified by the attended agent and judged, a test and a follow-up build on the same seed when the factory's code was wrong, a case or a seed when the model's behaviour was, or none with the reason. When every seed of the version is done, the attended agent revises this file, writes the version note's changelog, runs `uv run gate.py check` in the worktree, where a build git cannot list can still be amended, then fast-forwards `main` and runs `uv run gate.py release <version>`: the gate refuses until everything derived agrees, then cuts the annotated tag and renders `CHANGELOG.md`. The attended agent does not write code the factory could write and does not touch a test to make a build pass, because the factory's ability to do it is what is being measured; the tools refuse the model the same.

## Commands

- `uv run gate.py check`, `uv run gate.py render`, `uv run gate.py release <version>`: the gate. Problems go to stdout, one per line, starting with the path; exit 1 when there is any, 2 for a usage error, silence and 0 otherwise. `render` writes `CHANGELOG.md`. `release` also needs a clean tree, `AGENTS.md` changed since the previous tag, a green suite and at least one changelog bullet in the version note.
- `uv run python -m unittest -v`: the factory's own tests. Nothing external is needed.
- `uv run runs.py`: the records as a tab-separated table, one row per record, a header first; nothing is written. Any argument is a usage error.
- `uv run evals.py [--runs N] [case ...]`: the evaluation set, every case N times (three by default) in throwaway worktrees of this repository at `HEAD`, the case's files and test committed there first; one tab-separated table per case of counts (green, held out, honest, refused, passed by the case's word, a green case only when its held-out check passed too), medians (tool errors among them, the model's `error:` returns that no wall gave) and, beside the medians of requests, cost and seconds, their spread over the runs as `min-max`; after the table the set's pass rate and its standard error under a uniform prior. A case may hold `held_out/`, tests the model never sees, run after a green build. Needs the key and docker like a build; the records land in the store like a build's, the held-out check's files committed with them. Exit 1 when any run was capped or errored, 2 for a usage error.
- `uv run builder.py <checkout> "<goal>"`: one build, the goal text or the path of a seed, `docs/seeds/<name>.md`, whose `## Goal` is then the goal. Needs an instance configuration it can use, the key the configuration's `builder` role names, and docker, since the check runs in a container built once from the checkout's `uv.lock` and `check.Dockerfile`. Refuses a directory that is not a git checkout, a checkout with uncommitted or untracked changes, a configuration a run cannot use and a key file with no key, exit 2 and nothing made. When the model returns, the builder checks the tree it left unless nothing was written since the model's last check, so a record's `check` is the tree that was tested; then it compresses the wire, searches every file of the record for every key the configuration names, not only the one the run was given, and commits the record to the store, refusing to commit one it cannot search through. Exits 0 when the model returned a report, 1 on a cap, a provider error, or a record the store would not take. The cost and the time are in the record.
- `uv run build.py <repository> <branch> <seed>`: one build asked for through git. The branch is cloned into a directory of its own under the instance's `work`, the builder runs there, and a green check that changed something is pushed back to the branch as one commit of the factory's, never forced, its trailer naming the instance's version and the run; a build that is not green, one whose record the store would not take, or a branch that moved meanwhile leaves the branch alone, says why, exits 1 and writes the factory's note on the head it was asked of, `refs/notes/factory`, which `git notes --ref=factory show <commit>` reads. Nothing is left in `work` when the command ends. Exit 2 for what the builder cannot build: a repository git cannot read, a branch it lacks, a seed the branch does not hold or one without a Goal, a project with no `check.Dockerfile`.
- `git worktree add <path> -b <branch>`: a checkout for a build. `.claude/worktrees/` is an ignored place for one.
- `git push origin main --tags`: the mirror is `git@github-joam:yellow-robots/factory.git`. `github-joam` is an SSH alias on this host that selects the owner's key; two GitHub identities share the machine.

## Not derivable from the repository

- `docs/` is an Obsidian vault the owner keeps open. `backlog.base` changes whenever the owner adjusts a view, a filter or an order there, and a note's frontmatter is re-serialised when a property is edited there, in Obsidian's own shape; a frontmatter value that is not valid YAML, such as a bare `{{date}}`, does not survive that. A dirty `docs/` is the owner's content: read the diff and commit it as theirs.
- Four build commits of v0.7 and v0.8, cea0753, 5f7349f, 92191cc and 2a13022, wrote `Built-By` with a blank line between the trailers, which git's trailer parser does not read: `git log --format='%h %b' | grep '^Built-By:'` finds every build, `%(trailers:key=Built-By)` misses those four. They stay as they are: the gate reads the builds since the highest tag, so it never reads them, and it would refuse a release that carried one.
- A version exists only as a tag. Commit 48cbbe4 is titled `v0.4`; it is one change released in v0.4, not the version.
- The notes of v0.1 to v0.4, their changelog and the records before v0.5 say world for the checkout and plane for the tools; those were the observer's words.
- Branches `bootstrap` and `v0.1` to `v0.3` are leftovers of past worktrees and share their names with the tags, so git warns and prefers the tag. Write `tags/v0.3` where it matters.
- The model the builder runs on is the one the configuration gives the role `builder`; on this host it is DeepSeek `deepseek-flash`. pydantic-ai does not know that name, so `builder.py` carries a profile override keyed on it, and genai-prices has no row for it, so the price table in `builder.py` is the cost source; a role on another model has neither, and what that costs is the seed that adds it. Thinking is on by default and ignores temperature. No key is ever printed or committed.
- The history before this repository, v1 and the design that was abandoned for it, is in the owner's Obsidian vault at `/srv/obsidian/vaults/obsidian/03 archive/factory-v1/`. Reference, never a plan.
