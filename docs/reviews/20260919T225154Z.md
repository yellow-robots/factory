## Findings

### A capped run is pushed on a check that never saw the tree it left

severity: defect
verified: yes
judged: seed the-check-that-could-not-run

`check_final` swallows every exception -- `except Exception: pass`, with the correct reason that a sandbox which cannot run must not lose the record -- so when the builder's own final check cannot run, `check` keeps whatever the model's own last check said, which is a verdict on an earlier tree. Nothing in the record says the final check was skipped.

Until this version that decided nothing, because a capped run was refused whatever its check said. [[the-work-a-capped-run-leaves]] makes `check == "green"` the whole acceptance test, and capped runs are by construction the runs likeliest to have written since their own last check, which is exactly the condition that makes `check_final` the only checker there is.

Reproduced by the attended agent twice: by reading `builder.py`, where the swallow is four lines and unconditional; and by a test that edits, checks green, writes something the check has never seen and is capped with a sandbox that has nothing left to give. It fails on `'green' == 'green'`. That test is committed red as `test_a_green_the_final_check_could_not_confirm_does_not_push_the_tree`, and the seed it names is in this version.

### The security boundary is tested only against an empty store

severity: defect
verified: yes
judged: test test_a_record_the_store_would_not_take_is_refused_though_the_store_holds_other_commits

`_record_taken` is correct and the attended agent could not break it. The tests around it were blind. Both that cover a refused record ran with one record in a brand-new store, so the store sat on an unborn HEAD at the moment of the refusal, and every weaker reading passed them.

Reproduced: a mutant asking `rev-parse --verify HEAD` -- has the store any commit at all -- in place of asking for the record's own path ran all 201 tests green, and then pushed a record holding the key onto the branch. The guard now committed kills it, confirmed both ways: green on the old suite, red on this one. The setup the boundary needed was one build taken before the one refused.

### A check that never ran is a clause of the Goal that no test pins

severity: defect
verified: yes
judged: test test_a_capped_run_whose_check_never_ran_is_refused_though_it_changed_the_tree

Of the five things the Goal says must still refuse, four are exercised and `check == "none"` is exercised nowhere. It is the clause a real capped run is likeliest to reach, since a run capped in the middle of writing has often not checked at all.

Reproduced: a mutant refusing only `red`, dropping the `none` case, ran all 201 tests green while pushing a tree no check had ever seen. The guard now committed kills it, confirmed both ways.

### The store is asked a weaker question than the one that matters, and asked without a guard

severity: smell
verified: yes
judged: seed what-a-refused-build-says-and-asks

Two things about the same function, both read in the code by the attended agent.

`_record_taken` asks whether a path named `<stamp>` is in the store's HEAD tree, not whether the store accepted the commit for this record. Those coincide only because `commit_record` commits with a pathspec -- `builder.py:1280`, `commit -q -m <name> -- <name>` -- so a refused record left staged cannot be swept into HEAD by the next build. The boundary holds, and it holds on an invariant two modules away that no test states.

And it calls `_run` unguarded, on the path of every build including green ones, while every other `_run` on that path is wrapped. `_run` has `timeout=120` and so raises `TimeoutExpired`, and raises `FileNotFoundError` if git goes away. Its own docstring says a store that cannot answer "answers no"; a git that cannot run does not answer no, it raises through `main`. The direction is safe -- nothing is pushed -- but the build leaves no note and does not exit through `refused()`.

### A failed capped build's note no longer says the run was capped

severity: smell
verified: yes
judged: seed what-a-refused-build-says-and-asks

`refused(how)` prints the reason for the refusal and `_leave_note` writes that line. Before this change a capped run was refused first, so the note said "the run was capped"; now the capped run falls through and the note carries the substantive reason instead. AGENTS.md says the note is "one line naming the record and how it ended", and how it ended is the part that is gone, so this is a regression against the documented behaviour rather than a matter of taste. The record still names it, so nothing is lost -- only put one hop further away, and asymmetrically with the success case, where `Stopped-By` was added in this very change to say exactly that.

### The Goal does not ask that a run ending in an error still refuses

severity: smell
verified: yes
judged: none: kept deliberately; it has cost one record in the factory's history and the acceptance surface is worth more than the record

The Goal's headline is "A build is taken when the tree it left passes the check, whatever ended the run", and its enumerated list of what must still refuse -- a red check, a check that never ran, a green check that changed nothing, a branch that moved, a record the store would not take -- does not include a run that ended in an error. `build.py` refuses it anyway, and the pre-committed tests demand that it does, so the build followed the tests over the Goal's letter.

Verified by reading both texts. Kept, and the reason recorded here rather than inherited: across 190 records the store holds exactly one run that ended in an error with a green final check, worth $0.028, against seven capped ones worth $0.896. A cap is a stop at a known boundary with the tree in a known state; an error is an unknown failure, and what the model was doing when it happened is not known. Widening the acceptance surface for one record ever is not a trade worth making. Read "whatever ended the run" as "whatever cap ended the run".

## Where nothing was found

`Built-By` still reads exactly as it did. The second trailer is invisible to the gate: `BUILT_BY` matches `^Built-By[ \t]*:` and `_build_trailers` asks git for that key alone, so the line-count cross-check is unaffected. The attended agent ran `gate._commit_build_problems` against a real two-trailer commit and got no problems, and confirmed `%(trailers:key=Built-By,valueonly)` returns the value unchanged. `stopped` is set in three places and can only be `answer`, `cap` or `error`, and `error` never reaches the trailer, so `cap` is the only value ever written -- a newline or an injected second `Built-By` is unreachable, and both would fail closed at the gate regardless.

The security boundary itself held against every route tried: a record on disk never committed, an unborn-HEAD store, a store git refuses, a store that is not a repository, a concurrent build committing between the refusal and the lookup, a record name that is not what is looked up, and a divergence between the builder's store and the one `build.py` captured. Each refuses, and each fails in the safe direction. The two soft edges are the finding above.

The reordering changes the set of note-writing failures by exactly one case -- capped, green, with a diff, which is now a success and correctly leaves no note. One thing was gained and is worth naming: a capped run whose record the store refused now writes the leak's path into the project's note where it used to write "the run was capped", and `refused()` strips the store's absolute path and never carries the value, which is pinned by `test_nothing_leaves_the_instance_holding_the_key_s_value`.
