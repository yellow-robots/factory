The three builds of [[caps-for-the-checkout-as-it-is]], reviewed together as one change: the diff of `builder.py` and `runs.py` from ea4d147 to 66d9310, against the seed's Goal and the tests that pin it. The reviewer was told what was deliberately left out, so the constants that answer for nothing and the size of a read are not findings here. Every finding below was reproduced by the attended agent before it was written down.

Two of the eight are defects and both are the spec's rather than the build's: the code does what the Goal says, and the Goal was wrong. That is worth saying plainly, because the seed exists to stop runs being cut off and one of the two leaves them cut off.

## Findings

### The landing does not fire when a response carries more calls than the reserve

severity: defect
verified: yes
judged: test test_a_response_of_any_size_still_lands

pydantic-ai admits or refuses a whole response's tool calls together: it adds the response's call count to the projected usage and checks that against `tool_calls_limit` before any of them runs. So a response of `k` calls, issued with `s = budget - calls` of the budget left, either runs entirely or not at all. The tools' refusal can only be delivered when `s < k <= s + RESERVE`; when `k > s + RESERVE` the library raises and the model is never told to report. That is the failure the seed exists to remove, moved from the request limit to the tool-call limit.

Reproduced with an obedient model -- one that reports the moment any tool return says `report now` -- at this checkout's real budget of 128 and `RESERVE = 4`. A final response of 4 calls lands: `stopped: answer`, a report, 127 requests of 138. A final response of 5 does not: `stopped: cap`, no report, 125 requests of 138. Two calls a turn and a final response of 16: `stopped: cap`, no report, and **80 of the 138 requests unspent**. The run had done everything and paid for all of it.

It is live rather than theoretical. Of 3,635 responses carrying tool calls across the store's 181 records, 29 carried more than 4 -- sizes of 5, 6, 7, 8, 9, 14 and 16 -- and one of them is 20260918T231137Z, a capped run this seed's own evidence cites. The crossing also has to fall badly, so the risk a given run loses this way is a few tenths of a per cent; what it costs when it does is the whole run.

### One pass over the checkout is not the lines divided by the lines a read returns

severity: defect
verified: yes
judged: none: the test that held it, `test_one_pass_is_the_reads_the_tools_would_answer_with`, went with the formula it corrected when [[the-walk-that-bounds-nothing]] removed `call_budget` in v0.18. The finding was true and was fixed; what it was true of no longer exists.

`call_budget` divides the checkout's total lines by `READ_LINES_CAP`, as though one read could span two files. A read never does: it answers about one file. On this checkout the formula calls one pass 45 reads; the reads the tools would actually answer with, file by file, are 170, or 173 once `READ_BYTES_CAP` is applied too. So `PASSES = 2` does not buy two passes over the checkout. The budget's 128 leaves 90 calls for looking after the writes and the checks, which is **0.52 of a single pass**, and the version note's "the reading and the reading again" is wrong by about four times.

The error grows with the number of files rather than with their size, because a checkout of many small files costs one read each and the formula cannot see that: two hundred files of one line are two hundred reads and the formula calls them one.

Reproduced by simulating `read`'s own chunking over the exact file set the tools reach: 145 files, 13,469 lines, 173 reads for one pass; the ten largest files alone cost 35.

### The requests have six of headroom, and a tenth of past runs ran below it

severity: smell
verified: yes
judged: none: the reserve that the first finding requires widens the margin to 0.78 calls a request, below the store's lowest observed 0.85, so this closes with that fix rather than on its own; if it ever bites, the record says `cap: requests` and that is what the seed says that value means.

To spend the budget, be told to report and then report, a run must fit 128 calls inside about 136 requests, which is 0.94 tool calls per request. Build runs in the store hold a median of 1.22, but the minimum is 0.85, and 9 of 90 are below 0.94. The runs that actually reached a cap were all at 0.98 or better, so it is a tail, not the common case.

### The budget a run is given can disagree with the budget its tools carry

severity: smell
verified: yes
judged: none: the test that held it, `test_the_budget_a_run_is_given_is_the_budget_its_tools_carry`, went with the budget itself when [[the-walk-that-bounds-nothing]] removed it in v0.18. There is no number left for a caller and the tools to disagree about.

`run(agent, goal, budget=None)` falls back to `CALLS_FLOOR` when the caller names no budget, while the tools carry the checkout's. A caller that forgets the third argument reproduces the pre-change fault exactly: on a checkout of forty thousand lines the tools refuse at 200 while the library cuts the run off at 84, and the landing never fires. `main` passes `tools.budget` and is the only caller in the program, so nothing is broken today; what is wrong is that the two numbers can differ at all.

### README documents the constants that were removed

severity: smell
verified: yes
judged: seed the-readme-the-gate-never-reads

`README.md` still read "80 tool calls, 60 provider requests in the library; a cap hit in the library ends the run with no report". The numbers are gone, the source is now the checkout, and the tools land the run before the library sees it. The gate never reads README, so `check` was silent and `release` would have cut the tag over it. Corrected in this version by the attended agent; the seed is for the gap that let it through.

### `which_cap` answers by matching the library's English

severity: smell
verified: yes
judged: seed which-cap-from-the-numbers-not-the-words

It looks for `tool_calls_limit` and `request_limit` as substrings of the exception's message. Every branch is right against the pinned library, including cost and token limits and an empty detail, which correctly answer with neither. But the record's `cap` is a substring match on an exception's wording, and the first library bump that rewords either sentence turns every later record's answer into the empty string with the suite green.

### The two caps in the record are not the same kind of number

severity: smell
verified: yes
judged: test test_the_record_carries_the_caps_beside_the_counts_they_bound

`requests_cap` is the library's hard limit, which `requests` can never exceed. `calls_cap` is the budget the tools enforce, which `tool_calls` legitimately exceeds by up to the reserve: a landed run records 132 calls against a cap of 128. Side by side in the table they read as one kind of thing. The test's `assertLessEqual(tool_calls, calls_cap)` holds only because that run never reaches the reserve, so it asserts something that is not true in general.

### The budget's walk and the tools' walk are the same policy written twice

severity: smell
verified: yes
judged: seed one-walk-for-what-the-tools-can-reach

`call_budget` and `Tools._files` skip symlinks, skip anything with a `.git` component at any depth, and apply the hidden names at the root only. They agreed on every file of a tree built to separate them. They agree because they were written to the same words, and the budget's whole claim is that it counts what the tools can reach.

## Where nothing was found

The landing itself, from the tools' side: all six increment the count as their first statement and consult the budget before any work, every refusal counts including path, argument and protected-write refusals, and past the budget all six give the exact message, move no counter, never touch the sandbox and change no file. There is no internal caller of the six, and `check_final` correctly stays outside the count, being the builder's and not the model's. A budget of N allows exactly N working calls, consistent with the message and with the write cap's own shape. `request_limit` cannot fall to or below `tool_calls_limit` for any integer budget. `call_budget` does not follow symlinks, cannot leave the root, returns instantly on a directory cycle, answers the floor for a missing, empty or non-directory root, and takes 11 milliseconds here and under a second on a tree of twenty thousand files. The write cap and the check cap keep their own words and numbers, and their refusals still start `error: cap reached`, so the table keeps counting them as walls rather than tool errors. And no build touched a test: the three commits changed `builder.py` and `runs.py` only.
