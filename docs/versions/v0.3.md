# v0.3: the builder

The observer evolved into a cold session that changes a world until its tests pass. From here on
the factory is the builder: the attended agent writes the goal and the red tests, the factory
writes the code, the attended agent reviews the diff. The last version built by agents.

## Changelog

- Five functions: `list`, `read`, `write` (create or replace, parents inside the world), `edit`
  (exactly one occurrence), `check` (the world's tests in a container, no network, world read-only,
  exit code and tail returned, full log kept). Every failure is an `error: ...` string.
- Walls in the plane: paths outside the world; hidden roots `runs`, `.claude`, `__pycache__`,
  `.venv`, `plans`, `.git`; protected `test*.py`, `tests/`, `pyproject.toml`, `uv.lock`,
  `check.Dockerfile`; 30 writes and edits and 8 checks per run; 80 tool calls and 60 requests in
  the library.
- The check runs `python -P -m unittest discover` because a world-root `unittest.py` would
  otherwise turn any suite green; the image is built once from the world's own lock, with git
  because the world's tests use it.
- The record grows by `diff.patch` (against HEAD, plus a diff per untracked file), `check-<n>.log`,
  and numbers for writes, edits, checks, the plane's own verdict on the last check next to the
  report's claim, and the diff counts. No temperature in the request.
- 37 acceptance tests written from the plan before the code; the code written to pass them; an
  independent review found a writable `.git` and a forgeable green, both closed and pinned.
- First runs: G1 green in 3 edits and 2 checks ($0.009, 32 s), its diff merged as the first change
  built by the factory; G2, a test that cannot pass, red with no edits and an honest report.

# Factory v0.3: the builder

## Context

v0.2 (`main` 26eb3e8, tag `v0.2`) is the observer on pydantic-ai: a cold session that reads a
world through `list` and `read` and returns a typed report; the record holds the wire, the
messages and the numbers. It cannot act.

v0.3 evolves the observer into the **builder**: the same loop, plane and record, with three more
functions (`write`, `edit`, `check`), a world handed in as an argument, and a goal that is reached
when the world's tests pass. From v0.3 on the factory is the builder: the attended agent plans,
writes the spec and the red tests, creates the worktree and instantiates the factory; the factory
does the one step in between; the attended agent reviews the diff, verifies, merges and tags.
v0.3 itself is the last version built by agents, because v0.2 cannot write.

Weak self-improvement starts here: the world the builder edits is the factory's own repository.

Self-contained version: a cold agent gets this plan and the repository, nothing else.

## Facts established (2026-09-15)

- **Host.** Docker 29.8.0, rootful daemon, apparmor + seccomp default profiles, `jbrey` in the
  `docker` group (root-equivalent on the host; the containers themselves run as `jbrey`'s uid).
  Unprivileged user namespaces are blocked for unconfined binaries
  (`kernel.apparmor_restrict_unprivileged_userns=1`; `unshare -Urn` fails), so `unshare` and
  `systemd-run --user` cannot isolate the network. `bubblewrap` is not installed (apt candidate
  0.9.0; its AppArmor profile permits userns). uv 0.8.0 with `uv export`. Python 3.12.3.
- **Library.** pydantic-ai-slim 2.43.0 as pinned; see `plans/pydantic-ai-facts.md`. A tool that
  raises kills the run, a tool that returns a string is an ordinary result; `Literal` fields work in
  output models; `UsageLimits(tool_calls_limit, request_limit)` raise `UsageLimitExceeded`;
  `capture_run_messages` keeps the history on any exception; `ModelSettings.extra_body` passes
  provider-specific body fields.
- **DeepSeek.** Thinking mode is on by default at effort `high` for `deepseek-flash`. In thinking
  mode `temperature`, `presence_penalty` and `frequency_penalty` "will not trigger an error but
  will also have no effect": our `temperature: 0` in v0.1 and v0.2 did nothing. `reasoning_content`
  must be passed back on every subsequent request or the API returns 400; the library does this.
  Profile override from v0.2 kept (upstream issue #8353 open).
- **Reference builder prompt.** mini-SWE-agent's system template is one sentence ("You are a
  helpful assistant that can interact with a computer."); the work lives in the instance message:
  the task, a numbered workflow (read relevant files, reproduce, edit, verify, edge cases, submit
  with an explicit command), and execution rules. Short, structured, task-adjacent, no persona.

## Decisions (recommended; strike any you disagree with)

1. **One role, one file.** `builder.py build <world> "<goal>"`? No: `builder.py <world> "<goal>"`.
   The observer role is not carried; the builder observes before it writes. A read-only role, if
   ever wanted again, is a role text plus a tool subset, not a program. Naming of files and roles
   evolves when there is more than one role.
2. **The world is an argument.** A directory, required to exist; in practice the worktree the
   attended agent hands in. The record lands under the factory's own `runs/`, outside the world by
   construction. `HIDDEN` at the world root as in v0.2 **plus `.git`** (review finding: a writable
   `.git/hooks` is model code running on the host the next time the human runs git there; the
   record's diff is made by the factory with the git binary and is unaffected).
3. **Five functions.** `list`, `read` as in v0.2; `write(path, content)` creates or overwrites a
   text file (parents created inside the world); `edit(path, old, new)` replaces exactly one
   occurrence of `old`, else returns an error naming the count; `check()` runs the world's tests
   in the sandbox and returns the exit code and the tail of the output. Every error is a returned
   `error: ...` string, never an exception. `check` is how the builder knows the goal is reached.
4. **Protected paths.** The plane refuses `write`/`edit` on `test*.py` (unittest's own discovery
   pattern, any depth), anything under `tests/`, `pyproject.toml`, `uv.lock` and `check.Dockerfile`:
   the goal's criteria and the toolchain are the human's. Deterministic, tested, not prose.
5. **The goal.** Text passed on the command line (what and why, in a few sentences) plus the tests
   in the world. *Reached* is `check` green: every test passes, the human's red ones included,
   with no protected file touched. *Accepted* is the attended review of the diff against the
   goal's text, since green tests are a floor, not the spec. Nothing else defines it in v0.3.
6. **Check runs in a Docker container, world mounted read-only.** This sandboxes the check only;
   it is not how the factory is installed or run (that is a later version, undecided). Image
   `factory-check:<12 hex of sha256(uv.lock + check.Dockerfile)>` built once from
   `check.Dockerfile` (`python:3.12-slim`, `pip install` of `uv export --frozen --no-hashes`),
   with network; the check itself runs `docker run --rm --network none --user <uid>:<gid> -e
   HOME=/tmp -e PYTHONDONTWRITEBYTECODE=1 -v <world>:/w:ro -w /w --memory 1g --cpus 2
   --pids-limit 256 <image> python -P -m unittest discover -q`, subprocess timeout 120 s then
   `docker kill` (30 s). `-P` keeps the world off `sys.path` while the standard runner is imported:
   without it a world-root `unittest.py` written by the model turns any suite green (review
   finding, reproduced in the real sandbox). The image build has a `.dockerignore` so the context
   is the toolchain, not the world's `.venv` and records. Model-written code never runs on the
   host and cannot reach the key or the network. The record's diff is `git diff HEAD` (staged
   changes included) with a `--no-index` diff per untracked file. Alternatives
   weighed: `bubblewrap` is lighter (no daemon, no image, host venv bind-mounted read-only) and is
   the better long-term fit, but needs `sudo apt install bubblewrap`; `unshare`/`systemd-run` are
   blocked by the userns policy; gVisor and Podman are not installed. The `Sandbox` class is the
   only place that knows Docker, so swapping to bubblewrap later is one class.
7. **Caps.** `UsageLimits(tool_calls_limit=80, request_limit=60)`; plane caps `CHECK_CAP = 8` and
   `WRITE_CAP = 30` (writes + edits), after which the function returns `error: cap reached ...;
   report now`. A cap hit in the library ends the run with no report, as in v0.2.
8. **The builder stops itself.** It calls `final_result` when check is green or when it gives up.
   The plane records the truth independently: `numbers.check` is the last check's exit code
   (`green`/`red`/`none`) next to the report's own `check` claim. A mismatch is a measure.
9. **The record grows by the diff.** After the run the factory runs `git diff` and `git status
   --porcelain` in the world (read-only git, not exposed to the model) and writes `diff.patch`;
   `check-<n>.log` per check; numbers add `world`, `writes`, `edits`, `checks`, `check`,
   `files_changed`, `insertions`, `deletions`, `check_seconds`.
10. **The prompt is a versioned instrument, not a belief.** Structure follows the reference: one
    short role sentence, the tools and what their results mean, a numbered order of work, the
    stopping rule, the report shape, a handful of rules. Its hash is in every record; changing it
    is a version; its effect is read off runs, which is how "does it matter" gets answered. No
    persona, no few-shot, no long rule lists. Text (fixed in `builder.py`):

    > You are the builder. You are given a goal and a world: a directory with code and tests. You
    > can explore it with `list` and `read`, change it with `write` and `edit`, and test it with
    > `check`. The goal is reached when `check` is green: the tests are the goal's acceptance
    > criteria and cannot be changed.
    >
    > Work in this order: read what the goal touches; run `check` once to see what fails; make the
    > smallest change that can make it pass; run `check`; repeat. Stop when `check` is green, or
    > when you cannot make it green within the budget, and return the report through the
    > `final_result` function: changed (the paths you wrote or edited, in order), did (what you
    > changed and why, one fact per item, each naming a path), check (green or red), failing (test
    > names if red), unsure (what you could not determine or verify).
    >
    > Rules: change only what the goal needs; prefer `edit` over `write` for existing files; never
    > work around a failing test by changing what it asserts; no commentary outside the report.

    Output model `BuildReport(changed: list[str], did: list[str], check: Literal["green", "red"],
    failing: list[str], unsure: list[str])`, rendered to `response.md` as five sections.
11. **Model settings tell the truth.** `temperature` is dropped (no effect in thinking mode);
    thinking stays at the API default; `timeout` 180 s. Numbers keep `reasoning_tokens`.
12. **Tags** `v0.3` at the merge. The factory's first build (G1 below) becomes `v0.4` after review,
    the first version built by the factory.
