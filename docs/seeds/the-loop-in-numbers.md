## Idea

A reader beside `runs.py`, per version and per seed of it: the builds git lists by their trailer, with their records' cost and seconds; the red commits before and after the first build; the reviews, their findings by severity and by what they became; and the commits by who made them, the factory's by their trailer and the attended agent's the rest, so the share of the loop's commits the factory made is a number that moves as responsibilities do. The version note's counts are read from it and no longer counted by hand. It reads the records where records-outside-the-project keeps them and git for the rest, and a step a role takes over later, the analyst's spec or the reviewer's note, shows in it by the trailer its commits carry.

## Goal

What a version took is a command, derived from git, the store and the vault, and never counted by hand.

**Build order, because a cold run that reads everything first spends its cap before its first write.** Stage one, reading only `repo.py` and `test_repo.py`'s `test_the_commits_between_two_points_oldest_first`: what `repo.py` gains. Stage two, reading `vault.py`'s `Note` and the `TallyTest` of `test_tally.py`: `tally.py`. Stage three, `gate.py`'s `USAGE` and `main` alone: the dispatch. Read `loop.py` only for the shape of its `gather`, and nothing else unless a test sends you there.

**`uv run gate.py numbers`** prints one tab-separated table: a header and one row per version, each tag in version order oldest first, and the version in flight last when there is one, named by its note. The columns, in this order: `version`, `seeds`, `runs`, `builds`, `green`, `red`, `capped`, `unrecorded`, `cost_usd`, `requests`, `reviews`, `findings`, `defects`, `judged_test`, `judged_seed`, `judged_case`, `judged_none`, `commits`, `by_hand`. `gate.py numbers <version>` prints the header, that row, and the unknown lines; a version that is neither a tag nor in flight is a usage error, exit 2. Exit 0; it writes nothing.

**Read as follows, and from nowhere else.** A version's commits are those after the previous tag up to and including its tag -- from the first commit for the first tag, and up to the head for the version in flight; `commits` is their count. A build is a commit among them whose `Built-By` trailer `repo.run_stamp` reads a stamp from; `builds` is their count and `by_hand` the commits that are not builds. `seeds`: the seed notes whose `version` names it. `runs`: the records of the store -- `instance.record_store()`, each `<store>/<stamp>/numbers.json` -- whose `seed` names one of the version's seeds: every run the version paid for, pushed or not, the red run whose tree was taken as base and the run a build refused among them, which is what the first build's own answer missed -- it counted builds git holds by trailer, so v0.21 read as 7 builds and $0.51 where its note counted 14 runs and $1.52, and the reviews of its red runs matched nothing. A record whose numbers cannot be read names no seed and is no run; one whose `seed` is null belongs to no version. `green`, `red`, `cost_usd`, `requests`: over the runs -- `numbers.json`'s `check`, and `cost_usd` and `requests` summed. `capped`: runs whose `stopped` is `cap`, or whose `messages.json` holds a tool return beginning `error: cap reached`, read through one reader `runs.py` gains beside `tool_errors`, so the two never disagree on a record. `unrecorded`: builds whose stamp has no readable record in the store; they count under `builds` and add nothing else. `reviews`: the review notes whose `runs` name at least one of the version's runs or builds; `findings` their level-three headings; `defects` those whose `severity` line is `defect`; `judged_test`, `judged_seed`, `judged_case`, `judged_none` from the `judged:` line, each comma-separated item by its first word, a finding counted once under each kind its line names however many items of that kind it names: `test a, seed b` once under each, `test a, test b` once under test. `green` and `red` are what each run's `check` says; a run whose check is neither -- `none`, a run that wrote after its last check -- counts under `runs` and under neither. A tag that is no version is no row, and its commits fall to the first version after it. Money is printed to four decimals, as `runs.py` prints it.

**Shape.** `tally.py` holds `gather(root) -> Tally`, a frozen dataclass of one `Row` per version and its `unknown` lines, gathered once through `vault`, `repo`, `instance` and `runs` and through nothing else -- no `subprocess`, no `open(`, no `.glob(`, no `read_text` of its own; the store's files are read through readers `runs.py` has or gains -- and `render(tally) -> str`, the table then `unknown: <field>: <why>` for each line, as `next` prints them. A fact that cannot be read is `None` with its line and never a value that means something else: a store the configuration does not name, and every store column is `None`, the review columns among them, since a review of a run git does not hold cannot be placed without the store and a count of the reviews git can place would mean something else; a git that cannot answer for a version's commits, builds or trailers, and that version's `commits`, `builds`, `by_hand` and `unrecorded` are `None`, never zero; a review note the vault could not read, or whose frontmatter it could not parse, and the review columns are `None` on every row with one line naming the note; a seed note or a version note the vault could not read, or whose frontmatter it could not parse, and every column that depends on a seed -- `seeds`, `runs`, the store columns and the review columns -- is `None` on every row with one line naming the note, since which version the note belongs to cannot be read either, and a version in flight whose note cannot be read has no row and one line; two version notes that are no tag, and no row is in flight, one line `in_flight: ...` as the loop says it, the tags' rows standing -- and a version note is what the loop calls one, a note whose type says `version`, so a note under `docs/versions/` the vault could not read is a line and never one of the notes counted. `capped` and `tool_errors` read a record's tool returns through one walk in `runs.py`, so they never disagree on what a tool return is; each record's numbers are read once, and `capped` is given the numbers it already has and reads the messages alone. An empty store is a store: zero runs, every build unrecorded, no line; the store that is unknown is one that is no directory or that the configuration does not name. A helper the module imports is used and not copied. `repo.py` gains `commits(root, since, to)`, the commits in order oldest first, `since` `None` for the beginning of history, and nothing it has changes. Nothing of this repository -- no seed's name, no version's, no stamp -- is written in the code or the tests.

**README and docstrings.** README's gate section names `numbers` beside `check`, `render`, `release` and `next`; `runs.py`'s docstring names `capped` as a reader and not a column of the table; `gate.py`'s `main` docstring names the command.
