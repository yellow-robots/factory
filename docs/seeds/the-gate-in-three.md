## Goal

`gate.py` becomes three modules with one responsibility each, typed results between them, failures that say what failed, and one formatter. Every test that is green today stays green; `gate.main(argv, root)` and `gate.USAGE` keep their names and their contract.

**`vault.py` reads the vault and nothing else.** A `Note` is a frozen dataclass -- `path`, `rel` (its path relative to the root, POSIX), `fm` (the frontmatter mapping, or `None`), `body`, and `error`, the words of the `OSError` when the file could not be read and `""` when it was, `fm` then `None` and `body` then `""` -- with `kind`, the frontmatter's `type` or `""`. `Vault` holds `root`, `docs` and the repository's listing of `docs/` -- what git lists, what git ignores -- and is made once by `Vault.read(root)`, which asks `repo` for the listing; `vault.notes()` reads and parses every note once and returns them as `Note`s, in path order, so no check parses a note a second time; `vault.holds(path)` is what `_in_vault` was and is `False` for a path outside the root; `vault.resolves(target)` is what `_resolve` was. `frontmatter`, `title`, `first_paragraph`, `changelog_bullets`, `review_findings` and `prose_lines` move here as they are, `prose_lines` sharing one fence walk with `review_findings`; the `.base` parser (`base_named` and what it uses) moves here whole. It imports `builder` for the Goal's reader and the fences, as the gate does today, and `repo` for the listing. The seed's and the review's field sets are read from the templates, once, and not written as constants a second time.

**`repo.py` reads and writes the repository and nothing else.** One shape for running a command: `Result(code, out, err)`, from `git(root, *args)`, which never raises -- a git that cannot start is a `Result` with a non-zero code and the exception's words in `err` -- and reads git with the same `-c` options everywhere, `_tag_date` and `_short_hash` included. A reader that needs git to have answered raises `RepoError`, carrying the command that failed and git's `err`, instead of an empty answer: `tags(root)`, `listing(root, docs)`, `builds(root, previous)`, `trailers(root, commit)`, `tag_date(root, tag)`, `short_hash(root, commit)`, and -- added after the first review, which found the three raw reads the gate still made were exactly the failures still silent -- `status(root)`, the uncommitted paths as `git status --porcelain` names them; `changed_since(root, tag, path)`, whether `path` differs between the tag and the head; and `message(root, commit)`, the commit's whole message. `RepoError.command` is a command, never a file's name. `err` is git's words on one line, runs of whitespace collapsed to one space, so a problem built from it is one line. `highest(tags)` and `version_key` are one function. `tests(root)` walks each `test*.py` at the root once and returns `Test(id, name, doc)` for every test method and class -- `id` as unittest names it, `module.Class.method` or `module.Class`, added after the loop's first build parsed the files again for want of it -- so a docstring, its name and its id are read together; a file that does not parse raises `RepoError` naming it. `suite(root)` runs the suite as `_suite_green` did and answers one of `green`, `red`, `timed out` and `could not run`; `tag(root, version, message)` is the git half of `_annotate` and returns its `Result`; `build_wheel(root)` and `wheels(dist)` move here, `wheels` raising `RepoError` on a `dist/` it cannot read.

**`gate.py` checks and commands.** A `Problem` is a frozen dataclass, `path` and `message`, printed as `path: message`; every check returns `list[Problem]`, deduplicated by value, and `main` prints them. `problems_check(root)` becomes a sequence of checks over one `Vault` and one list of `Test`s, each check a function of what it checks -- the wikilinks, one note, the version notes together, the base, the builds -- and `_release_problems` reuses the same `Vault` rather than parsing again. `problems_render` becomes `render(root) -> str`, the changelog's text, with the write in `main`; `_annotate` becomes the note's message in `gate.py` and `repo.tag`. After the first review: `gate.py` reads no file and runs no git of its own -- no `read_text`, no `subprocess`, no `repo.git(...)` -- every read going through `vault` and `repo`, and the module is imported by its name, `from vault import Note, Vault`, with no local named `vault`. `render` and the tag's message read the version notes through the Vault, so a note that cannot be read is one problem and nothing is written or tagged. The Vault is read once per command through one helper; the templates' field sets are read once per check into a typed value; problems are deduplicated by one function; `notes()` are in `Path` order, as `sorted(docs.rglob("*.md"))` gave them, and each note is read once per check, the wikilink scan reading the notes the Vault already holds.

**A failure is one problem naming its cause, never silence and never twenty.** A `RepoError` raised while checking is one problem, `<path>: <command> failed: <err>` -- git's words with any full hash in them abbreviated to seven characters, because a problem never names a commit by its full hash, which the release's tests hold -- where `<path>` is the thing being read -- `docs/versions/` for the tags, `docs/` for the listing, `test_x.py` for a test file that does not parse -- and the check goes on with what it has, so a tree that is no git checkout gets one line for the tags and one for the builds and none for the version notes. A note or a template that cannot be read is `<rel>: cannot be read`, once, and a template without frontmatter is `<rel>: no frontmatter`; either way nothing derived from it is reported as if it were empty, and the checks of that kind that do not derive from the template -- status, value, effort, the Goal, a finding's lines -- still run. A test file that does not parse is `<file>: does not parse`, its name once and no absolute path, and the tests of the other files still count, so a seed named by no test is still reported. A tag git could not create names git's own words, as the wheel's failure names uv's. The suite's problem says which of red, timed out and could not run it was, `test: the unittest suite is red` staying as it is for red.

**One formatter.** `pyproject.toml` already sets `[tool.ruff] line-length = 100`; `ruff check` passes and no `# fmt: skip` appears in the three modules. The check's image has no ruff, so `ruff format` is run by the attended agent on the green tree and committed as its own change, and the modules are written so that it has little to do. Every function has a docstring whose first line says what it returns or does. Functions precede their first use only where Python requires it; otherwise readers, then checks, then commands.

After the second review. The wikilink scan reads every file the vault holds -- templates, files that are no note, a note's frontmatter and a note with none -- whole and once, through the Vault, which holds every file's text beside its notes; the lines the old gate printed for a link to nowhere in any of them are printed still. A template that cannot be read, or has no frontmatter, is reported once by `problems_check` itself and not from inside the check of each note of its kind, so it is said with no such note too, and the base's check does not skip in silence. `render`'s failures are problems like any other: deduplicated, one per cause, and inside `release` caught and printed as one line with exit 1, the tag standing as after a failed wheel, never a traceback. `tests(root)` answers a typed value, `Tests(found, unparseable)`, `found` the tests and `unparseable` one `(file, why)` per `test*.py` that could not be parsed or read, its name once and no absolute path; it raises `RepoError` only when the root's files cannot be listed, and `loop.py`'s reading of it follows. A release precondition that cannot be read -- the status, the diff -- is filed under the version's note. No fallback that the types make unreachable stays in the code: no `else ""` for a note the preconditions already required, no guard for a `None` no reader answers.

What must not change: every line `check`, `render` and `release` print today for a problem that exists today, exactly as they print it, and the exit codes; `gate.main`'s signature; `gate.USAGE`; how many times git is asked for the listing (once per `check`) and for the builds (once per `release`), which two tests pin by patching `subprocess.run`.
