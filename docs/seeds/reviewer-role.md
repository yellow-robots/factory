2026-09-19, from the research commissioned on the stopping condition, read in `docs/scratchpad/review-depth-2026-09-19.md`: the intuition that how much must be read follows from the size or the entropy of a change does not survive the literature. No review stopping rule has ever been built from entropy, complexity or length; the one entropy result that works, ordering lines for inspection, was measured only after its authors discarded every fix of fifteen lines or more, because the signal fades on exactly the large changes a budget would be for. Two of its findings bear directly on this role. A model's own account of its confidence is not a stopping signal: measured calibration error runs from 0.09 to 0.73, a stated probability above ninety per cent has been measured against a bare majority of correct answers, and asking a model to reflect on its certainty scores worse in places than a constant guess. And repeated independent passes are the one intervention with a large measured effect: a single pass finds between a quarter and a third of what is there, five runs of one model over one change agreed on very little, and aggregating ten passes has been measured to more than double recall. Where a human team stops gaining at two reviewers, an automated one keeps gaining to ten — which is also what makes an estimate of what was missed available to us and not to them, since the estimator that works needs four or more independent readings.

## Idea

A second program of the factory's, beside `builder.py`: a cold model session over a delivered tree, read only, with a run recorded in the store like any other, because a role that cannot be measured cannot be given a responsibility.

**Consistency is the whole problem, and it is measured rather than asserted.** A reviewer that says different things about the same diff is not a gate. Four mechanisms buy four different kinds of consistency, and one instrument decides whether they worked.

**Its dimensions.** Not "review this change" but one pass per named dimension, each phrased as a goal the pass must pursue rather than a question it may answer briefly -- *find every place the change satisfies the test without meeting the goal*, not *does it meet the goal?*. The set is fixed, small, and earned: every dimension exists because something got through. From the last three days alone -- a change that met the assertion and not the Goal, twice; a function that duplicated a walk the program already had; a constant kept alive by a branch nothing reaches; documentation left describing what was removed. The failure-mode set in `cases/` is the rest of the catalogue, and a defect that slips through becomes a new case and then a new dimension. Whether a dimension is a goal or a question changes what is found is an open question with a cheap answer: run both phrasings over the same seeded diffs and count. That belongs in the first version of this role, not after it.

This is what buys consistency across different diffs: the same standard applied every time, and coverage a reader can see, because the note says which dimensions ran.

**Its reading is many readings.** Not one careful pass per dimension but several independent ones, each a cold session, none seeing another's findings. A finding carries the count of passes that reached it, and one that only a single pass found is not reported. This buys consistency across runs: a single pass is not made reliable, its spread is measured and the noise discarded. The research is unambiguous that this is the one intervention with a large measured effect, and that an automated reader keeps gaining where a human team stops at two.

**Every finding carries a reproduction, and this is the hardest rule.** A finding without a runnable probe is not a finding. It converts opinion into fact, it makes verification cheap for whoever must judge it, and it settles the thing agreement cannot: **agreement measures how thoroughly the change was read, reproduction measures whether what was found is real.** Several passes can agree on something false. A script that demonstrates the defect cannot be argued with. Both axes are needed and they are not the same axis.

**The deterministic layer runs first and the model never re-derives it.** Whatever a tool can decide -- duplication, dead code, coverage delta, complexity -- a tool decides, and its output is an input to the review rather than something a pass rediscovers. Tools do not drift, which is what buys consistency over time, and every pass spent re-deriving what a linter knows is a pass not spent on judgement. Those tools belong in the check first so the builder is held to the same gate: quality-checks. And the gate itself is the project's, not the factory's -- a project declares its own lint, format and types as it already declares how its tests run, and the factory runs what it finds rather than imposing a choice that would be wrong on first contact with someone else's repository. What this role adds on top is the judgement no project declares.

**Its depth is one number, fixed and recorded.** How many passes each dimension gets is chosen once, written into the run's record so two reviews are comparable, and changed only when the cases say it should be. It is not a setting the commissioner turns, because there is no evidence yet for what any depth buys -- the catch rate at any depth is the first thing this role must produce, and a knob offered before that number exists is complexity bought on a guess. Nor is the bias a setting: it leans harsh, and it says the same kind of thing every time, because a claim whose meaning changes with the commissioner is not comparable across runs.

**Its answer.** One claim, the same shape every time -- and not "this meets the contract", which no number of passes can warrant. What it says is what it found and how much agreement stood behind it, with the severity the notes already use. Whether that clears the bar is the commissioner's to decide: the reviewer informs the contract and does not settle it.

**What a finding becomes, and where it lives.** A finding above a severity the spec names does not become a note, it becomes a fixing round: a build on the same seed with the finding's reproduction as a red test, which is how the factory already answers a defect. Below that line, a finding becomes a test when the code was wrong, a case when the model's behaviour was, or a note with a reason. The review itself is a record and a note, as a build is, so what was found can be counted over versions.

It does not become a comment in the code, and the reasoning should be stated because the alternative is tempting. A future run is a cold session: it sees the tree, the tests and the goal, and nothing of what was said about them. So a comment reaches a future builder only if that run happens to read that file, and the median build reads six files of a hundred and fifty-six. A test reaches it with certainty, because the check is what the run is measured by. And a comment is stored where a test is executed: it goes stale silently, which is the decay this factory has already filed twice, in `stale-docstring-case` and in the-readme-the-gate-never-reads. Where a finding says the code's *meaning* is wrong rather than its behaviour, the docstring changes in the fixing round, which is a change the check can hold. The manager's copy is the review note, which the gate already reads. This is a decision rather than a fact, and it is the owner's to overturn.

**Its instrument: it is measured against diffs whose defects are known.** `cases/` is already a set of changes with seeded failures and held-out tests that know the right answer, which makes it the natural corpus: run the reviewer against them and count what it catches. A reviewer that catches nine of ten is a gate; one that catches four is theatre, and no amount of good prose in its report changes that. **This role does not ship until that number exists.** The same instrument answers the questions the design cannot answer by argument: whether a goal phrasing beats a question, whether five passes beat three, whether the stronger model is the better reviewer, whether reading the builder's record anchors a pass or informs it, and how suggestible a pass is when steering text is planted beside a defect. A dimension that never catches anything is dropped.

**What it answers, and its confinement.** Two questions a machine cannot: does the code do what its tests claim, or does it satisfy them without doing it; and what else did it change. Two machine preconditions run first because they are cheap and neither needs a model: the tests pass, and the tests are the ones that were commissioned rather than the ones delivered. It cannot write, cannot fix what it finds, cannot push and cannot spend -- a reviewer that could fix would become a builder and acquire an interest in finding less. It executes nothing of the project's, so it needs no container; the risk it carries instead is the text it reads, since code, tests and a seed can all carry instructions aimed at a model. That risk is bounded by the same confinement -- a compromised reviewer produces one wrong verdict, not a compromised machine -- and the dangerous direction is a false pass, which the commissioner's own run of the tests catches. The builder's record may be read as a lead and never stand as a ground.

**Its model.** Stronger than the builder's, which the instance's roles now express. That the stronger model is the better reviewer is a hypothesis and the cases answer it.

**When it stops, and what it is never asked.** The budget is the number of passes and nothing else. It is never asked how confident it is, and no threshold is put on a probability it reports: both have been measured and neither carries a usable signal. There is no principled amount of reading after which a change is known correct, so the honest rule is a fixed budget of independent readings and an honest account of how much they agreed.

**What is not this role.** Finding holes in defences is a separate commission with its own agents and its own goal, and it does not belong among these dimensions: a pass told to hunt for a way in is doing different work from a pass told to judge whether a change was well made, and mixing them makes both worse and neither measurable. It is its own seed when its turn comes.

**What waits.** Depth as something the commissioner chooses, against criticality and budget, once the cases have said what a depth is worth -- a dial on effort is legitimate where a dial on the standard is not, and the price of a pass falls every year while the value of quality rises, so the design should not be built around what a pass costs today. An estimate of what the passes missed, drawn from how little they overlap -- the one method that measures the unseen, and the one that needs the four or more independent readings an automated reviewer can afford. The verdict's place in the loop as a note beside a proposed commit, which is coordination and not this role. And its read-only tools are where `pydantic-ai-harness`'s `FileSystem(read_only=True)` is finally worth trying against the two the factory hand-wrote, judged by the runs, as the v0.2 plan said it would be when a version first needed it.

## How it is built

2026-09-20, the attended agent, reading `builder.py` for what this role would have to write from scratch. Almost none of it. The confinement, the wire, the record, the key scan before the store takes it, the agent and its limits, and the roles table that already lets a second role name a different model and key are all there and all tested. What this role adds is a lens that cannot write, a different report, and passes rather than a pass. That makes it four goals rather than a second program's worth, and they are ordered so each one is measurable on its own.

**A. It reads, and it cannot do anything else.** `reviewer.py <checkout> <seed> <base>` runs a cold session over the checkout with `list`, `read` and `search` and nothing else: `write`, `edit` and `check` are not refused at the wall, they are never offered, so the model is never told it has a hand it does not. It is given the Goal from the seed, the diff from `base` to the checkout's head, and one dimension, and it returns findings -- each a title, a dimension, a severity, the path it points at, and a reproduction. The run is recorded in the store as a build's is, wire and all, key-scanned before the store takes it, and a record it cannot search through is not committed. It builds no container and runs nothing of the project's. Exit 0 on a report, 1 on a cap or an error, 2 on what it cannot review.

**B. Several passes, and what they agreed on.** Each dimension is run more than once, each pass a cold session that sees nothing of the others. A finding carries how many passes reached it, and one that only a single pass reached stays in the record but leaves the report. Agreement is measured on what a finding *names* -- its dimension and the path it points at -- and never on its prose, because prose similarity is a second model's judgement and this number must not need one. It is a crude measure and the cases say whether it is crude enough to be wrong.

**C. The dimensions, and the note.** The fixed set, each phrased as a goal a pass pursues rather than a question it may answer briefly, and each one earned by something that got through. The review renders into `docs/reviews/` from the template the gate already reads, so what this role finds is counted the way the hand-written reviews have been counted since v0.2.

**D. The catch rate, which is the shipping gate.** `cases/` holds changes with known seeded defects and held-out tests that know the answer. The harness runs the reviewer over them and counts what it caught, and that number is what this role is. It also settles by measurement what the Idea above settles by argument: whether a dimension phrased as a goal beats one phrased as a question, whether more passes beat fewer, and whether the stronger model is the better reviewer. A dimension that catches nothing is dropped.

`quality-checks` is not underneath this and does not block it. The deterministic layer is an input this role reads when a project declares one and does without when it does not, which is the same thing it does for a project that declares no linter at all.
