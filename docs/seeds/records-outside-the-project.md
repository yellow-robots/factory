## Idea

The record stays with the factory. The builder writes it to a store the instance's configuration names, not a constant beside the program: a directory outside every checkout it builds, a git repository of its own to which each record is committed when its run ends, so the log is kept and read as git keeps it, and no record enters it holding the key's value, scanned for in every file of the record, the compressed wire read through. `runs.py` and `evals.py` read the same store. The project keeps what it can use, the build's commit and its `Built-By` trailer, whose stamp points into the store as a commit points at a CI run. The gate stops looking for records in the project: a build's trailer is checked for its shape as today, and the three reads of `runs/` go, the tree a trailer's stamp must have in HEAD, the directory a review's stamp must have, and the wire tracked uncompressed, which is the store's to hold if it is kept. That a build has its record is held by order and not by a lookup: the record is committed to the store before the build's commit leaves the instance (build-from-a-pushed-branch). The 146 records git tracks are carried to the store as its first commit and leave this repository's tree in one commit of the attended agent's, with the owner's yes; history keeps them and nothing is rewritten. The store is a repository apart, local and with no remote for now, the owner's decision of 2026-09-17; where it lives when the instance leaves this host waits with the owner's question of what a forge is here, and one fact bears on it: a forge grants reading by repository and not by branch, so a store apart can stay closed while the code is open. A record holds the project's content, the files read, the diff, the checks' output, so records of a project that is not the owner's need the project's leave, or are cut down to what holds no content, the numbers and the shape of the tool calls; nothing of that binds while every project is the owner's, and it is a seed of its own the day one is not.

## Goal

The gate reads no record in the project. A build's record is the factory's and is kept in the factory's store, outside the project; what the project holds of a build is its commit and the `Built-By` trailer, whose stamp names the record where the factory keeps it.

`gate.py` stops reading `runs/` in the repository it checks, in three places. A build's trailer is checked as today for how git reads it and for its value ending `run <stamp>` with the whole stamp in the builder's shape, and no stamp is looked up: no problem says a run has no committed record, and no problem of `check` or of `release` begins `runs/`. A review's `runs:` is checked as today for holding at least one stamp, each one path segment, one of them naming the note, and no stamp needs a directory `runs/<stamp>`. A wire tracked uncompressed under `runs/` is no problem, and `_wire_problems` goes. From the first review: with the lookup gone the stamp's shape is all that says a value names a run, so its digits are ASCII's, `STAMP_SHAPE` compiled with `re.ASCII` as `BUILT_BY` is, and a stamp in the digits of another script names no run; and the guard and the second set in `_commit_build_problems` that nothing can reach any more go. A repository with no `runs/`, with a `runs/` of any content, or with a file under it named like a stamp, is checked and released the same.

The builder keeps its records in the instance's store. The instance's configuration is a TOML file, the one the environment's `FACTORY_INSTANCE` names or, with none named, `.config/factory/instance.toml` under the home of whoever runs the program, found when the program runs and not when it is imported; its `records` is the absolute path of the store. `builder.py` has no `RUNS` and `runs.py` has none. A run whose configuration is missing, is not TOML, has no `records`, names one that is not a string or not an absolute path, or names a store that is inside the checkout or holds it, is a usage error that names the configuration's file and says which, exit 2, before the key is read, before a model is called and before anything is made.

The store is a git repository of its own, each record a directory at its root named by its stamp, as the builder names it today. A store that is not yet a git repository, its directory absent or plain, is made one when the first record is committed, not before: a run refused for its usage makes nothing. When a run ends, whatever ended it, the builder compresses the record's `wire.jsonl` to `wire.jsonl.gz`, the plain file gone, searches every file of the record, a `.gz` file read through its compression, for the key's value, and commits the record to the store: that record and nothing else in the commit, whatever else the store holds uncommitted, the commit's message the stamp, its author and committer `factory <factory@localhost>` so no identity of the host's is needed, git run with its environment cleaned as `git_env` cleans it. A record that holds the key's value is not committed: the builder names the file on stderr, never the value, and exits 1, and the record stays on disk. The first line the builder prints stays the record's path.

From the second review, its findings reproduced by the attended agent: the store's git is the factory's alone. It runs with the system and the global configuration files left unread and with no hook of the store's run, and a record's files are added whatever an ignore file of the host's or of the store's says, so a commit holds every file of the record. A commit the store refuses, for a lock left behind or a ref git cannot write, is a run reported and never a traceback: the record's path is the first line printed and the numbers line follows it, one line on stderr names the record and git's own words, the run exits 1, the record stays on disk with its wire compressed, and the store is left as the run found it, nothing of the record staged. A set reads such a run's record as it reads any other, its row the check the record holds, and exits 1.

From the same review: three configurations a run reads as usable and then falls over on, each now a usage error like the rest, exit 2, with no model called and nothing made, each in its own words, and the order of the three reads fixed. The configuration's own faults come first, before the key is read: a `FACTORY_INSTANCE` that is set and empty names no file and is refused, the home's configuration not read in its place, so only an unset variable falls back, and a configuration whose bytes are not UTF-8 is not TOML and its refusal names the file. Then the key: a file that cannot be read, or one holding no value, empty or a name with nothing after the `=`, is refused naming the key's file, since an empty key is a key no record can be searched for and that search is the wall that keeps the key out of the store; the search has no case for an empty key any more, and a key of one character is a key, whose record is not committed. Then the store's directory, made once the configuration is read and the key is a key: a `records` that is a plain file or a path the run cannot make is refused naming the configuration's file and the store's path.

`evals.py` writes `held_out.log` and `held_out.json` into a record after the builder committed it: they are committed to the store the same way, searched for the key's value too, by the one function of `builder.py` that commits a record, so a set leaves nothing of a record uncommitted; a stand-in for `builder.main` in the tests writes a record and commits nothing, and the same function commits all of it. That function is the one place a record is searched and committed, for the builder's own run too, and a file that is not what its name says, a `.gz` that is not gzip, is searched as the bytes it is; a record the harness cannot commit is a failed run, its reason on stderr as any other, never the key's value. `runs.py`, given no directory, reads the store the configuration names and is a usage error naming the configuration's file, exit 2, when there is none; given a directory it reads that; and the store's own `.git` is no record and no row.

The docstrings and comments of `gate.py`, `builder.py`, `runs.py` and `evals.py` that say where a record is kept or looked up say what is now true. The tests are the attended agent's and are not changed.
